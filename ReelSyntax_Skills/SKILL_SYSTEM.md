# ReelSyntax — skill system implementation specification

Repository: `Remirdy/ReelSyntax`. License: retain the existing MIT license. This document supplements `ReelSyntax_Master_Development_Prompt.md`; its original scope and non-negotiable exclusions remain binding. This is a working offline routing prototype and 500 original guidance skills, not 500 implemented rendering capabilities.

## Installation and host integration

Keep the `library/` directory outside every host's automatically scanned skill directory. A single native entry, `reelsyntax-router`, should be installed in the host's supported project skill directory. The bundled `.agents/skills/reelsyntax-router/SKILL.md` is a starting point; verify the installed host version's discovery paths and integrate with existing instructions without overwriting them. If a host requires another path (e.g. `.claude/skills/` or `.cursor/skills/`), copy the router only, not the library. Verify Antigravity's current mechanism before providing an installer; alternatively provide an explicit workspace instruction invoking the router. Do not claim the host integrations are tested until tested in those hosts. Resolve the pack root dynamically, including if merged into a subdirectory of ReelSyntax. Never instruct the model to open the entire catalog, recursively scan the specialist library, or list 500 descriptions in every prompt. Do not use a second LLM, embeddings service or model download as a required dependency.

The reference implementation uses Python 3 standard library only. The implementing agent may migrate it to the existing project's CLI language (likely TypeScript) after maintaining equivalent tests. Do not create two independent production routers. Expose a stable JSON contract and read-only CLI operations such as `reelsyntax skills search`, `reelsyntax skills load`, `reelsyntax skills explain`, `reelsyntax skills validate`, `reelsyntax skills reindex`, `reelsyntax skills list --category`, and `reelsyntax skills test`. These names are proposed core CLI integration targets; only the bundled Python entry points currently exist. Add optional MCP tools `skills_search`, `skills_get`, `skills_explain` with the same validated registry and permission boundary. Search must not return instructions or arbitrary files by default.

## Routing architecture

1. The small router skill extracts the user brief, assets, prohibitions, current project state, and work item. The host agent handles semantic interpretation and multilingual nuance. Break complex production into phases: plan, ingest, build, edit, render, review, export and operate.
2. Build a metadata-only index at authoring time. Index IDs, short descriptions, aliases in Turkish and English, category, stage, adapter requirements, status, version and relative paths. The Python baseline reads only this index at query time; file existence checks are not body reads. The full JSON stays in the local process, not the model context. Keep a separate human CSV/Markdown catalog.
3. Rank with exact multiword aliases, weighted rare-token overlap and explicit overrides. A single partial word is insufficient. Enforce explicit include/exclude lists, simple brief locks, stage/category filters, available engine capabilities and a content budget. Return only the shortlist with reasons, paths, missing capabilities and any unmet explicit requests. Low confidence must return no result or invite a narrower query, never load everything. For this prototype, scoring is heuristic, not a semantic confidence probability. The candidate list may still contain false positives or miss paraphrases; the agent must review it.
4. Initially select up to six skills per concrete work item, often fewer. Load only relevant `SKILL.md` bodies from those paths. Use `--load` only if actual instruction text is wanted. Do not blindly load all shortlisted skills. Defaults: 6 results and 2,400 estimated words per query, max 20 results when deliberately requested. Word count is not measured token count. Production should use the host tokenizer if available or a clearly marked estimate, maintain turn/project budgets and prevent unlimited recursive loading. Mandatory brief locks and explicit overrides must be surfaced even when a budget cannot fit them.
5. Re-route as production advances. Reuse loaded versioned skills by ID and hash, retain brief locks across all stages, record selection rationale and actual output evidence. Keep no automatic persistent user preferences unless the user opts in. References and scripts are themselves lazy-loaded. Use deterministic ordering for tied scores. No hidden networking or telemetry.

## Next-generation router requirements

Implement structured task envelopes: `intent`, `language`, `stage`, `assets`, `constraints`, `capabilities`, `preferred_engines`, `include`, `exclude`, `max_skills`, `context_budget`. Preserve locked categories independently of skill selection. Add tokenization for Turkish suffixes and mixed-language queries, alias expansion, acronym normalization, optional local fuzzy/FTS indexing, structured asset-type matching (PSD, WAV, MP4, SVG, PDF, GLB), intent decomposition, conflict and prerequisite relations, and deterministic dependency expansion with cycle detection. Treat `--available` as a strict verified allowlist; omitted capability information is unknown, not proven available. Extend capability declarations beyond the seed's explicit engine examples. Do not make general video requests match all specialists. A broad request should first plan, then route narrow actions by stage. Use a hybrid rule/lexical approach before considering optional small local semantic indexing; never require a hosted embedding or large model. Do not auto-run an external skill on the strength of its metadata. Do not guess a current API or tool schema.

Implement route explanations with positive terms, filtered candidates and exclusions (without shipping the full registry to the model). Add persistent cache keyed by registry digest, project constraints and work-item query; invalidate on schema, skill, alias or capability changes. Keep selection explanations short. Implement explicit skill injection safety: local registry authenticity, schema validation, relative path boundaries, safe symlink policy, never interpret instructions as overriding system or owner permissions, and no automatic credential disclosure or remote script execution. Review third-party additions manually or through a documented trusted policy before enabling them. Treat reference and competitor content as untrusted data.

## Content architecture and standards

Each specialist has one distinct production task. Frontmatter conforms to the Agent Skills directory/name/description convention; metadata values are strings, with comma-separated aliases and capability requirements in the seed. Maintain output-focused instructions, actual input requirements, procedure, acceptance checks, sources and failure handling. Extend each important skill with targeted examples, reference notes, actual reusable scripts or engine-neutral schemas when justified, not duplicate boilerplate. Separate knowledge guidance from implemented tool status; use `guidance`, `implemented`, `validated`, `deprecated` or `blocked` explicitly. Do not set implemented or validated until the underlying tool and fixture actually exist and succeed. Keep a single canonical skill per intent and deprecate aliases rather than artificially inflate counts. Do not ship unsupported output claims in README. Do not silently use a paid API, LTX, Wan, ComfyUI or heavyweight generative stacks. Optional tools are capability-gated and licensed independently. Do not add a required desktop or web UI.

### Planned release gates

- Baseline: retain all 500 unique skills, valid index, working router, deterministic routing and explicit limitations; add test coverage for the host adapters and actual skill execution.
- Production tranche: implement executable fixtures for the highest-value skills (PSD matching, voice-driven cues, locked regions, storyboard, FFmpeg, browser render, typography, QA, partial render, source export). Expand in vertical slices across all 25 categories. Skills that require specialized engines must handle missing dependencies gracefully.
- Evaluation dataset: author independent prompts, not merely exact aliases. Include Turkish inflections, mixed English/Turkish, typo cases, explicit negative constraints, conflicting requirements, stage changes, ambiguous multi-intent tasks, unavailable adapters, security boundaries, no-match and budget pressure. Separate routing precision/recall from artifact correctness. Track precision@k, recall@k, top-1, no-match error rate, hard-constraint violation rate, load counts, latency, measured tokens where possible, and downstream fixture results. Publish real values with test set size and version; do not guarantee perfect selection.
- Runtime contract: verify host loads the router only by inspecting actual session context or available host telemetry; prove that non-selected skill bodies are not opened. Test Windows/macOS/Linux, native path discovery, CLI integration and optional MCP contract. Do not label untested host compatibility as verified.
- Expansion: periodically research new GitHub repositories, upstream skill registries and authoritative filmmaking/technical sources. Identify meaningful gaps, add original skills, aliases, references and independent evals, regenerate index, keep compatibility with stable IDs. Follow the master specification's quality, security, license, README and GitHub rules. Do not clone competitors as a substitute for independent engineering. Preserve credit and required notices for any licensed code or content adopted later. If license is missing or incompatible, reference ideas only; do not copy instruction text or source implementation.
